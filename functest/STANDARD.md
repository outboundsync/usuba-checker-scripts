# Usuba Standard v0.2: what a working Omarchy plugin is

Target: Omarchy 4.0.4-1 (shell tree byte-identical to basecamp/omarchy@c668141), Quickshell + Qt 6.11 as installed on the reference Dell.

The Usuba Checker (functest/) enforces this standard: static checks (static_checks.py, dell_checks.py, usuba/checks.py), task-contract checks (rescore.py) and a real-shell runtime probe (runtime.py). Every failure the checker emits starts with a rule id from this document and ends with a `Fix:` hint.

Levels: **error** always fails. **high** is a heuristic finding that fails (it is reported as `heuristic/high` so a human can overrule it). **medium**/**low** heuristics are warnings only.

The type and member allowlists (USB-Q01, USB-A01, USB-A02, USB-A04) are generated by `usuba/build_types.py` from the qmltypes/qmldir files of the Qt 6.11 and Quickshell builds the runtime uses and from Omarchy 4.0.4's shell/Commons and shell/Ui, so they move with the Dell rather than with a hand-kept denylist.

## Task contract

### USB-T01: Answer contains plugin code
- Level: error
- Rationale: A manifest alone (or an empty answer) installs nothing that runs; the old grader passed manifest-only answers on chunk tasks because the upstream tree supplied the code.
- Failing example: `### manifest.json only, for "Write a complete Omarchy plugin ..."`
- Fix: return the QML entry point(s) the manifest names, in full
- Checked by: rescore.task_findings

### USB-T02: Requested file is delivered
- Level: error
- Rationale: When a task asks for a specific file, the answer must contain that file with a real implementation.
- Failing example: `"Implement `HomeContent.qml` in full" -> answer contains only manifest.json`
- Fix: return the complete requested file
- Checked by: rescore.task_findings

### USB-T03: Answer is files, not leaked reasoning
- Level: error
- Rationale: Long prose or self-correction ('Wait', 'Actually') before the first file means the output is a draft, not a deliverable; extraction is unreliable.
- Failing example: `Wait, actually the Loader... ### Panel.qml`
- Fix: return only `### path` headings with fenced code
- Checked by: rescore.py

## Manifest

### USB-M01: manifest.json is valid JSON with an id
- Level: error
- Rationale: Omarchy refuses to register a plugin it cannot parse.
- Failing example: `trailing comma in manifest.json`
- Fix: fix the JSON
- Checked by: static_checks

### USB-M02: Entry points are QML files
- Level: error
- Rationale: Quickshell loads QML only; a .js/.py entry point never loads.
- Failing example: `"entryPoints": {"barWidget": "main.js"}`
- Fix: point entryPoints at .qml files
- Checked by: static_checks

### USB-M03: Plugin ships QML
- Level: error
- Rationale: A plugin with no QML has nothing for the shell to instantiate.
- Failing example: `manifest + tablet.py only`
- Fix: add the QML entry points
- Checked by: static_checks

### USB-M04: Entry root is a shell surface
- Level: error
- Rationale: ApplicationWindow/Window roots open a desktop app window instead of a bar widget/panel/overlay.
- Failing example: `ApplicationWindow { ... } as barWidget`
- Fix: use Item / BarWidget / Panel (qs.Ui) as the root
- Checked by: static_checks

### USB-M05: Namespaced, non-reserved id
- Level: error
- Rationale: Third-party plugins must use a namespaced id outside omarchy.*.
- Failing example: `"id": "time-machine"`
- Fix: use e.g. "jankeesvw.time-machine"
- Checked by: rescore (fix_manifest)

## QML types and imports

### USB-Q01: Every QML type resolves (positive allowlist)
- Level: error
- Rationale: A type that no imported module provides makes the component fail to load. The allowlist is built from the real Qt 6 / Quickshell qmltypes and Omarchy qs.Commons/qs.Ui QML (usuba/types.json), plus the plugin's own QML files, qmldir entries and inline components.
- Failing example: `layer.effect: DropShadow { ... } with only `import QtQuick`; `Process { }` without `import Quickshell.Io``
- Fix: add the import that provides the type, or use a type that exists
- Checked by: usuba/checks.py

### USB-Q02: Imports exist
- Level: error
- Rationale: Importing a module that does not exist (or an Omarchy module other than qs.Commons/qs.Ui) breaks loading.
- Failing example: `import qs.Services`
- Fix: import only Qt 6, Quickshell, qs.Commons, qs.Ui or shipped files
- Checked by: static_checks

### USB-Q03: No Qt 5 APIs
- Level: error
- Rationale: Omarchy runs Qt 6; Qt 5 modules are absent.
- Failing example: `import QtGraphicalEffects 1.15`
- Fix: use Qt5Compat.GraphicalEffects or QtQuick.Effects
- Checked by: static_checks

### USB-Q04: Valid QML structure
- Level: error
- Rationale: QML objects cannot be declared inside JavaScript blocks.
- Failing example: `Component.onCompleted: { Timer { } }`
- Fix: declare objects in QML, start them from JS
- Checked by: static_checks

### USB-Q05: QtObject does not host child objects
- Level: error
- Rationale: QtObject has no default property, so Timer/Process/FileView declared inside it is a load error. From expert review (UC-QML-04).
- Failing example: `QtObject { Timer { interval: 1000 } }`
- Fix: use an Item root or `property Timer t: Timer {}`
- Checked by: usuba/checks.py

## APIs

### USB-A01: Only real APIs are called
- Level: error
- Rationale: Invented JS APIs throw at runtime, usually on a click path the smoke test never exercises. Members of `Qt.*` and `Quickshell.*` are checked against the real objects; calls on capitalised names must hit a singleton, JS import or id in scope. A small denylist of observed hallucinations backs this up.
- Failing example: `Quickshell.exec([...]).then(...); Qt.clipboard.text = s; Service.call("x", "y")`
- Fix: use Process / Quickshell.execDetached / omarchy-shell IPC / wl-copy
- Checked by: usuba/checks.py

### USB-A02: Signal handlers name real signals
- Level: error
- Rationale: A handler for a signal the type does not have never fires (or fails to load). Signals come from the type's qmltypes/QML definition plus its prototype chain.
- Failing example: `Process { onFinished: ... }  (Process has exited/started)`
- Fix: use the type's real signal, e.g. onExited, or StdioCollector.onStreamFinished
- Checked by: usuba/checks.py

### USB-A08: Read-only bar facade properties are not assigned
- Level: medium (warning)
- Rationale: Warning only: 4 Dell-verified working plugins do this inside guarded code. Third-party plugins receive the read-only PluginBarApi facade; assigning a readonly member throws and aborts the function (e.g. close() leaves a keyboard grab). From expert review (UC-QML-01).
- Failing example: `bar.centerHoverRevealSuppressed = true`
- Fix: bar.setCenterHoverRevealSuppressed(true)
- Checked by: usuba/checks.py

### USB-A03: QML types are not constructed with `new`
- Level: error
- Rationale: `new SequentialAnimation()` is not valid QML JavaScript.
- Failing example: `var a = new NumberAnimation()`
- Fix: declare the object in QML with an id
- Checked by: usuba/checks.py

### USB-A04: Methods called on ids exist
- Level: error
- Rationale: Calling a method the object's type lacks throws a TypeError.
- Failing example: `proc.start()  // Process has no start()`
- Fix: use the real method/property (running = true)
- Checked by: usuba/checks.py

### USB-A05: No Node/browser/C++ idioms in QML JS
- Level: error
- Rationale: require(), fetch(), document.*, QProcess etc. do not exist in Quickshell.
- Failing example: `const cp = require('child_process')`
- Fix: use Process / XMLHttpRequest
- Checked by: static_checks

### USB-A06: qs.Commons singleton members exist
- Level: error
- Rationale: Color/Style/Util/Border members that the real singleton lacks are undefined.
- Failing example: `Color.accent2`
- Fix: use a member that exists in shell/Commons
- Checked by: dell_checks

### USB-A07: Only real `shell` members are used
- Level: error
- Rationale: Omarchy injects a fixed shell object (PluginShellApi / shell.qml root); any other member is always undefined.
- Failing example: `shell.system.exec(...)`
- Fix: use members listed in the Omarchy 4.0.4 PluginShellApi
- Checked by: usuba/checks.py

## Binaries and commands

### USB-B01: Binaries in shell strings exist on the Dell
- Level: error
- Rationale: `sh -c`/`bash -c` strings, os.system strings and shipped shell scripts are parsed; every command word must be on the Dell's PATH (dell_env/system_bins.txt + omarchy_bins.txt), shipped, or documented as a dependency.
- Failing example: `["sh", "-c", "playerctl status | head -1"]`
- Fix: use an installed tool, ship a script, or document the dependency in README.md
- Checked by: usuba/checks.py

### USB-B02: No X11-only tools
- Level: error
- Rationale: Omarchy is a Wayland/Hyprland session; xinput, setxkbmap, xdotool, onboard, xclip, xrandr ... do nothing or are missing.
- Failing example: `subprocess.run(["setxkbmap", "de"])`
- Fix: use hyprctl / wtype / wl-copy / a Wayland OSK
- Checked by: usuba/checks.py

### USB-B03: hyprctl / hyprsunset invocations are valid
- Level: error
- Rationale: Invented subcommands fail silently.
- Failing example: `hyprctl background add x.png; hyprsunset enable`
- Fix: use real hyprctl commands; hyprsunset -t 4500 / hyprctl hyprsunset temperature 4500
- Checked by: usuba/checks.py

### USB-B04: No hyprctl reload after hyprctl keyword
- Level: error
- Rationale: `hyprctl reload` re-reads hyprland.conf and discards the runtime keywords just applied.
- Failing example: `hyprctl keyword general:gaps_in 4; hyprctl reload`
- Fix: drop the reload
- Checked by: usuba/checks.py

### USB-B05: argv[0] exists on the Dell
- Level: error
- Rationale: A Process whose program is not installed never starts.
- Failing example: `command: ["walker"]`
- Fix: use an installed program or ship/document it
- Checked by: dell_checks

### USB-B06: CLI flags are real
- Level: error
- Rationale: Invented flags make the tool print usage and exit, so the feature silently does nothing.
- Failing example: `fcitx5-remote -l`
- Fix: use flags from the tool's real getopt/--help on the Dell
- Checked by: usuba/checks.py

## Shipped files

### USB-F01: Referenced helper scripts are shipped
- Level: error
- Rationale: A command that runs bin/foo.sh or scripts/x.py the plugin does not contain fails at click time.
- Failing example: `command: ["bash", Qt.resolvedUrl("bin/speed.sh")] with no bin/speed.sh`
- Fix: ship the script or inline the command
- Checked by: usuba/checks.py

## JavaScript correctness

### USB-J01: No undeclared identifiers
- Level: error
- Rationale: Assigning or dereferencing a name that is never declared is a ReferenceError; wrapping it in try/catch only hides that the feature shows nothing.
- Failing example: `try { const w = shell.wm.windows } catch (e) {}`
- Fix: declare the property and fill it from a real API
- Checked by: usuba/checks.py

### USB-J03: No Qt.resolvedUrl("~")
- Level: error
- Rationale: resolvedUrl resolves relative to the QML file and never expands ~.
- Failing example: `Qt.resolvedUrl("~/.config/x")`
- Fix: use Quickshell.env("HOME") or StandardPaths
- Checked by: usuba/checks.py

### USB-J04: argv paths are local paths, not URLs
- Level: error
- Rationale: Qt.resolvedUrl returns file:///...; passed to a program as a path it does not exist.
- Failing example: `command: ["bash", Qt.resolvedUrl("x.sh")]`
- Fix: strip the file:// scheme (e.g. .toString().replace(/^file:\/\//, ""))
- Checked by: usuba/checks.py

### USB-J06: Loader-passed properties are not read only in onCompleted
- Level: error
- Rationale: Properties set on Loader.item after load arrive after Component.onCompleted, so code that reads them only there always sees defaults.
- Failing example: `onLoaded: item.vaultPath = p  // child reads vaultPath only in onCompleted`
- Fix: use setSource(url, {props}) or react in on<Prop>Changed
- Checked by: usuba/checks.py

### USB-J02: Commands never receive undefined
- Level: error
- Rationale: argv built from bar.<x>/settings.<x> that do not exist passes the string 'undefined'.
- Failing example: `command: ["x", settings.mode] with no `mode` default`
- Fix: declare manifest defaults / use real PluginBarApi members
- Checked by: dell_checks

## Safety

### USB-S01: Writes outside the plugin dir are flagged
- Level: warn (high: protected config/system paths; medium: other paths outside plugin data dirs)
- Rationale: Changing Hyprland/Omarchy config, /etc, /usr or shell rc files can surprise the user or break the session, but some plugins legitimately do it (e.g. a theme or keybind tool) - so it is a warning the reviewer must read, not a failure.
- Failing example: `echo ... >> ~/.config/hypr/hyprland.conf`
- Fix: prefer hyprctl keyword / omarchy-shell IPC; if a write is the point of the plugin, say so in the README
- Checked by: static_checks.py / runtime.py

### USB-S02: Privileged or remote-exec commands are flagged
- Level: warn (high)
- Rationale: sudo/pkexec need a password prompt (a bar click just fails) and curl|sh runs unreviewed code; both are legitimate in installers, so they warn rather than fail.
- Failing example: `["pkexec", "systemctl", ...]`
- Fix: do not escalate from the shell; document manual steps or use a polkit-free path
- Checked by: static_checks.py

### USB-S03: No clearly destructive commands
- Level: error
- Rationale: rm -rf of $HOME, ~ or / destroys user data; this is the only safety case that stays a hard fail.
- Failing example: `rm -rf $HOME/`
- Fix: never delete outside the plugin's own data dir
- Checked by: static_checks.py / runtime.py

## Review warnings (from HANCORE findings)

### USB-W01: Programs the plugin runs are documented dependencies
- Level: warn (low; EXPERIMENTAL, off by default)
- Rationale: Runs a program that a stock Omarchy install lacks and the README/manifest/PKGBUILD never mention; HANCORE's most common finding family (install-deps-packaging). Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.47, recall 0.32 (base rate 0.35).
- Failing example: `command: ["playerctl", "status"] with no README mention`
- Fix: list every external program (with its pacman/AUR package) and probe `command -v` before use
- Checked by: usuba/hancore_rules.py

### USB-W02: No hardcoded secrets or tokens
- Level: warn (medium; on by default, maintainer override)
- Rationale: Known token formats (ghp_, github_pat_, sk-, AKIA, xox*, AIza, private keys) or long literals assigned to key/token/secret/password names leak credentials to every user. Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.43, recall 0.01 (base rate 0.27).
- Failing example: `const apiKey = "sk-proj-..."`
- Fix: read secrets from the keyring (secret-tool) or a 0600 config outside the plugin
- Checked by: usuba/hancore_rules.py

### USB-W03: Remote code is pinned
- Level: warn (medium; EXPERIMENTAL, off by default)
- Rationale: curl|sh, git clone without a pinned SHA/tag, pip install git+URL without @ref, raw.githubusercontent main/master, releases/latest and unversioned npx run code that can change after review. Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.42, recall 0.05 (base rate 0.20).
- Failing example: `curl -fsSL https://x/install.sh | bash`
- Fix: pin to a full commit SHA or versioned release and verify a checksum
- Checked by: usuba/hancore_rules.py

### USB-W04: File operations are safe
- Level: warn (medium; EXPERIMENTAL, off by default)
- Rationale: World-writable chmod, forced symlinks, predictable /tmp paths and rm -rf on an unchecked variable allow symlink/TOCTOU attacks or data loss. (rm -rf of $HOME/~// itself is USB-S03, a fail.) Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.37, recall 0.14 (base rate 0.32).
- Failing example: `echo $x > /tmp/state.json`
- Fix: use mktemp or $XDG_RUNTIME_DIR, 0600/0700 modes, refuse symlinks, validate variables before rm -rf
- Checked by: usuba/hancore_rules.py

### USB-W05: Privileged actions are flagged
- Level: warn (medium; on by default)
- Rationale: sudo/pkexec/doas/run0, system-level systemctl, writes to /etc, /usr, /boot or /opt, and setuid modes; HANCORE asks for these to be removed or documented as manual steps. Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.60, recall 0.32 (base rate 0.24).
- Failing example: `["pkexec", "tee", "/etc/foo.conf"]`
- Fix: stay unprivileged; document manual root steps in the README
- Checked by: usuba/hancore_rules.py

### USB-W06: Rich text is not bound to untrusted data
- Level: warn (medium; EXPERIMENTAL, off by default)
- Rationale: Text.RichText/StyledText/MarkdownText render links and images, so text from commands, files, the network or other apps can inject markup. Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.21, recall 0.05 (base rate 0.18).
- Failing example: `textFormat: Text.RichText; text: notif.body`
- Fix: use textFormat: Text.PlainText for non-literal text, or escape it
- Checked by: usuba/hancore_rules.py

### USB-W07: No interpolation into shell or Lua command strings
- Level: warn (medium; EXPERIMENTAL, off by default)
- Rationale: Concatenating or templating values into sh -c, eval, os.system/shell=True or hyprctl dispatch strings is command injection when the value comes from data. Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.17, recall 0.13 (base rate 0.10).
- Failing example: `["sh", "-c", "notify-send " + title]`
- Fix: pass values as separate argv elements, or quote them
- Checked by: usuba/hancore_rules.py

### USB-W08: Network calls and processes have timeouts
- Level: warn (low; EXPERIMENTAL, off by default)
- Rationale: curl/wget without --max-time, requests/urlopen without timeout, and XMLHttpRequest without xhr.timeout can hang the widget forever. Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.26, recall 0.11 (base rate 0.22).
- Failing example: `curl -s https://api/x`
- Fix: add --max-time / timeout= / xhr.timeout, or wrap in `timeout 10`
- Checked by: usuba/hancore_rules.py

### USB-W09: Remote URLs use https
- Level: warn (medium; EXPERIMENTAL, off by default)
- Rationale: Plain http:// to a public host sends data without TLS (loopback and LAN addresses are exempt). Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.27, recall 0.03 (base rate 0.18).
- Failing example: `http://api.example.org/v1`
- Fix: use https://
- Checked by: usuba/hancore_rules.py

### USB-W10: Input is bounded
- Level: warn (low; EXPERIMENTAL, off by default)
- Rationale: StdioCollector/FileView/SplitParser output read with no size cap anywhere in the file can exhaust memory on huge output. Measured against HANCORE findings on 4011 non-holdout plugins: precision 0.37, recall 0.30 (base rate 0.39).
- Failing example: `FileView { path: log } with no cap`
- Fix: cap the bytes read (head -c N, slice) before parsing
- Checked by: usuba/hancore_rules.py

## Heuristics (graded)

### USB-H01: Real data, not simulated
- Level: high/medium
- Rationale: Code that says its data is simulated/mock/fake is a stub. High (blocking) when the wording is explicit or the plugin has no data source at all; medium otherwise.
- Failing example:

```
// Safe simulation: avoids calling external binaries
status = "Up to date"
```
- Fix: read the real source (Process, FileView, Quickshell service)
- Checked by: usuba/checks.py

### USB-H02: No hardcoded readings shown as live data
- Level: high/medium
- Rationale: A literal like "22°C" or "45%" in a Text is a placeholder. High when the plugin has no IO at all.
- Failing example: `text: "☀️ 22°C"`
- Fix: bind the text to a property filled from a real source
- Checked by: usuba/checks.py

### USB-H03: Handlers do something besides console.log
- Level: high/low
- Rationale: A plugin whose only side effects are console.log calls is a stub. High when there is no IO anywhere and >=3 logs; low for noisy logging.
- Failing example: `onClicked: console.log("toggled")`
- Fix: make each handler perform its action
- Checked by: usuba/checks.py

### USB-H04: No demo click handlers
- Level: high
- Rationale: A click handler whose only action is reporting the click (notify-send "Clicked", console.log) is a placeholder.
- Failing example: `onClicked: execDetached(["notify-send", "Clicked at"])`
- Fix: make the click do what the plugin is for
- Checked by: usuba/checks.py

### USB-H05: Not a placeholder UI
- Level: error
- Rationale: All UI handlers empty/no-op, handlers calling empty functions, or a trivial plugin with no IO/data/interaction.
- Failing example: `onClicked: {}`
- Fix: implement the behaviour
- Checked by: static_checks

### USB-H06: No placeholder data patterns
- Level: error
- Rationale: Lorem ipsum, Item 1/2/3, John Doe, random numbers presented as metrics.
- Failing example: `model: ["Item 1", "Item 2"]`
- Fix: use real data
- Checked by: static_checks

### USB-H07: No placeholder endpoints or credentials
- Level: high
- Rationale: example.com URLs or YOUR_API_KEY ship a plugin that can never reach real data.
- Failing example: `url: "https://api.example.com/v1"`
- Fix: read endpoints/keys from settings or real config
- Checked by: usuba/checks.py

## Runtime

### USB-R01: Loads and registers in the real shell
- Level: error
- Rationale: The plugin must load, register and instantiate every entry point without QML errors.
- Failing example: `"Foo is not a type", "failed to load"`
- Fix: fix the reported QML error
- Checked by: runtime

### USB-R02: No runtime JS/QML errors
- Level: error
- Rationale: TypeError/ReferenceError/binding errors during startup and the interaction probe.
- Failing example: `TypeError: Cannot read property 'x' of undefined`
- Fix: guard the value or use the real API
- Checked by: runtime

### USB-R03: Visible, legible, on-screen
- Level: error
- Rationale: Bar widgets/panels must draw something visible, inside the screen, with legible contrast and non-zero size.
- Failing example: `zero-size bar widget`
- Fix: give the widget implicit size and theme colours
- Checked by: runtime

### USB-R04: Runtime commands are valid
- Level: error
- Rationale: Processes run during the probe must exist on the Dell and receive defined arguments; no writes outside the plugin's area.
- Failing example: `exec: walker does not exist on the Dell`
- Fix: use installed programs and defined args
- Checked by: runtime

## Dell-learned (v0.2)

Added after the 30-batch Dell hardware sweep (5,526 isolated loads; dell/sweep/DELL_LEARNINGS.md). Levels follow the precision each check
reached against Dell labels; none reached blocking precision except the two runtime failure conditions.

### USB-D00: Severity of shell messages (fatal vs warning)
- Level: rule for runtime and Dell labels
- Rationale: on the Dell, plugins logging `Unable to assign [undefined] to int`, read-only-property TypeErrors, ReferenceErrors inside bindings or anchor warnings rendered and toggled fine (7/7 answer-key WORKS). Only messages that stop a component from being created broke plugins.
- Failing example: `Panel.qml:12:5: Fancy is not a type` (fatal) vs `Panel.qml[317:21]: Unable to assign [undefined] to int` (warning)
- Fix: fix fatal load errors first; warnings still deserve a fix but do not fail the plugin
- Checked by: runtime.DOWNGRADE, dell/sweep/build_results.FATAL (answer key 52/52)

### USB-D01: Do not rewire the user's global audio graph
- Level: medium (warning; precision 0.16 vs Dell broken, the harm lands on the desktop shell)
- Rationale: pennyfx.audio-control's EQ daemon retargeted the default sink and rebuilt PipeWire filter nodes every 5 s; the desktop shell went into a socket-notifier storm and was OOM-killed at 13 GB, ending the Hyprland session.
- Failing example: `pw-metadata -n default <node> target.object <id>`, `pactl load-module module-null-sink`, `wpctl set-default`
- Fix: change only nodes the plugin owns, restore the previous default on exit, never loop on rebuilding nodes, document the side effect
- Checked by: dell_learned.check

### USB-D02: Panels and overlays answer the shell's toggle
- Level: medium (warning; precision 0.33, recall 0.12 vs Dell "toggle opened no surface")
- Rationale: `shell toggle <id>` calls the entry's toggle/open; without one the Dell showed nothing after a successful IPC toggle.
- Failing example: `PanelWindow { visible: false }` as the panel entry with no function toggle()
- Fix: add `function toggle()` (and open/close) or an IpcHandler to the panel/overlay root
- Checked by: dell_learned.check

### USB-D04: Usage cycle
- Level: error if the shell dies during the cycle; errors logged during it are reported with a `usage:` prefix
- Rationale: 82 Dell bugs appeared only through interaction (68 toggles that opened nothing, 14 errors only in panel/overlay code).
- Failing example: `shell died during the usage cycle USB-D04 (close/reopen via IPC)`
- Fix: make open/close idempotent; guard state used by the panel
- Checked by: runtime (summon, close, reopen, probe P3)

### USB-D05: No runaway memory
- Level: warning above 150 MB RSS growth in the ~9 s probe window, error above 300 MB
- Rationale: Dell median shell RSS is 284 MB; 11 of 4,596 instances grew >150 MB in 20 s. Box warning tier: precision 0.75, recall 0.27, 0/60 control false alarms.
- Failing example: `runaway memory USB-D05: shell RSS grew 412 MB in ~9 s after the plugin loaded`
- Fix: reuse objects, cap models/caches, destroy() dynamically created items
- Checked by: runtime

A rule is on by default only if its plugin-level precision against HANCORE is >= 0.5 and at least 0.10 above the category base rate (hancore/rule_metrics.json; holdout plugins excluded). Only W05 met that bar. W02 (hardcoded secrets) measured 0.43 but is on by default by maintainer decision: a committed key is worth flagging even when HANCORE does not comment on it, and as a warning it can never fail a plugin. The rest are experimental (run with experimental=True / --experimental). None of them fail a plugin; USB-S03 is still the only hard-fail safety rule.
